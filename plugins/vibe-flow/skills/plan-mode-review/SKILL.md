# Процедура Plan Mode

Запреты («НЕ вызывать `ExitPlanMode`, пока…») стоит продублировать в `CLAUDE.md` проекта — тогда они действуют, даже если скилл не загрузился.

**Порядок:** написать план в файл → **проверить живьём допущения о внешних системах** (LIVE FACTS RULE) → запустить пачку ревьюеров (одним сообщением, параллельно), **каждый выставляет балл и число блокирующих по рубрике** → когда пачка вернулась — `vibe-flow:orchestration-router` **отдельным сообщением** → задать пользователю обязательные вопросы → `vibe-flow:codex-plan-critic` (внешнее ревью на другой модели, если Codex установлен) → **гейт по классу дефекта** → показать упрощённый план + секции ревьюеров + разбор замечаний критика + вердикт по оркестрации → `ExitPlanMode` только после одобрения.

🔴 **Гейт двух моделей:** если Codex CLI установлен, план уходит в реализацию, только когда **ни у ревьюеров Claude, ни у внешнего критика не осталось открытых замечаний `critical`/`high`**. Одна модель не пропускает план в одиночку. Codex не установлен — гейт держат ревьюеры Claude (см. CODEX CRITIC RULE). Балл считается и показывается, но гейтом не является — почему именно так, см. PLAN GATE RULE.

## LIVE FACTS RULE

**Каждый план обязан выписать свои допущения о внешних системах и проверить их живьём — ДО ревьюеров и ДО `ExitPlanMode`.**

**Откуда правило.** В одном реальном плане предикат «запись относится к нужной категории» читал не то поле внешнего API — с похожим именем, но другим смыслом: по нему нужная запись была неотличима от посторонней. Это прошло **девять проходов ревью**: шесть ревьюеров Claude и три раунда внешнего критика. Никто не мог поймать — проверка требовала живого запроса к API, а ревьюеры читают текст. План честно писал «какое поле годится — проверить первым делом при реализации», и на этом все успокоились. Дефект доехал до прода и был пойман смоуком в браузере. **Девять проходов по тексту не заменили одного живого запроса.**

**Что считается допущением о внешней системе** — любое утверждение о том, чего нет в нашем коде и что нельзя вывести чтением репозитория:

- имя, тип или семантика поля во внешнем API (платёжка, CRM, учётная система, телефония, почта, карты, LLM-провайдер);
- что именно вернёт эндпоинт или отчёт: набор значений, единицы, знак, часовой пояс, включены ли налоги, есть ли пагинация;
- как называется сущность в чужом справочнике (счёт, тип оплаты, статус, роль);
- фактическое состояние прода: есть ли строки в таблице, у скольких пользователей включён флаг, какие значения реально встречаются.

**Секция `## 🔬 Проверить живьём` обязательна в плане**, если такие допущения есть. Формат — таблица, где каждая строка закрывается **фактом**, а не намерением:

```markdown
## 🔬 Проверить живьём

| Допущение | Чем проверено | Факт | На что влияет |
|---|---|---|---|
| Признак «заказ оплачен» — поле `status` в ответе API платежей | Запрос `GET /orders/{id}` по тестовому заказу, ключ из окружения | ❌ неверно: `status` — статус доставки. Оплату несёт `payment.state = "captured"` | Предикат «выдать чек»: по неверному полю чек получал и неоплаченный заказ |
| Флаг `beta_reports` включён только у двух клиентов | Запрос к БД: выборка клиентов с включённым флагом | ✅ 2 строки | Охват фичи, нужна ли миграция данных |
```

- **«Проверим при реализации» — не заполнение строки.** Такая формулировка и есть тот самый дефект: она переносит проверку туда, где её уже никто не потребует
- **Проверять дёшево:** запрос к API, одноразовый скрипт или запрос к БД. Минуты — против раунда ревью в десятки минут. Примеры:
  - API: `printf 'header = "Authorization: Bearer %s"\n' "$API_TOKEN" | curl -sS -K - https://api.example.com/v1/orders/123` — токен берётся из окружения и не попадает ни в argv, ни в историю shell
  - БД: одноразовый скрипт, который читает ключи из окружения (`node --env-file=.env …`, `python` с `dotenv`, `psql` с `PG*`-переменными)
  - **Временный скрипт удалить за собой**, как только факт вписан в план
- 🔴 **Секреты — только из окружения:** никаких токенов литералом в `curl`, в `-e`/`-c`-коде и в аргументах — они остаются в истории shell и в логе сессии
- 🔴 **Живая проверка — только чтение.** Запись во внешнюю боевую систему ради проверки допущения — по явному «да» пользователя
- 🔴 **Живая проверка идёт ДО пачки ревьюеров**, а не после: ревьюеры должны читать план с уже подставленными фактами. Иначе они снова будут проверять текст на непротиворечивость самому себе
- **Чего проверить нельзя** (нет доступа, нет тестового аккаунта, эффект виден только после записи) — строка остаётся с явным `⚠️ не проверено` и **обязательным запасным путём** в плане: что делает код, если допущение окажется неверным. Непроверенное допущение без запасного пути — блокирующее замечание (`high` по рубрике)
- **Ревьюеры проверяют полноту, а не правильность:** их дело — заметить допущение, которого в таблице нет. Правильность уже установлена фактом
- **Самоисключение:** план без обращений к внешним системам (чистый рефакторинг, вёрстка, переводы) секцию не заводит

## REVIEW BATCH RULE

**АВТОМАТИЧЕСКИ** запускать пачку ревьюеров после того, как план записан в файл и живые факты подставлены, но **ДО `ExitPlanMode`** — **одним сообщением, параллельно** (несколько вызовов Agent в одном ответе), не последовательно. Каждому передать путь к файлу плана и блок про рубрику (см. PLAN SCORING RULE). `vibe-flow:orchestration-router` в пачку **не входит** — он запускается **отдельным сообщением после того, как вся пачка вернулась** (см. ниже).

| Ревьюер | Что проверяет | Что дописывает в план |
|---|---|---|
| `vibe-flow:plan-reviewer` | Пересказ плана простым языком + ТОП-3 варианта; полнота секции `## 🔬 Проверить живьём` | Короткую секцию с баллом; упрощённый план — в ответе |
| `vibe-flow:access-control-reviewer` | Кто увидит новую фичу/раздел/данные: роли, права, изоляция между пользователями/клиентами, RLS, флаги включения | `## 🔒 Контроль доступа` + при необходимости вопрос пользователю |
| `vibe-flow:test-impact-reviewer` | Какие тесты обновить, какие добавить, или тесты не нужны | `## 🧪 Влияние на тесты` |
| `vibe-flow:security-reviewer` | Уязвимости, авторизация/аутентификация, инъекции, XSS, небезопасные эндпоинты и вебхуки, секреты | `## 🛡️ Безопасность` |
| `vibe-flow:performance-reviewer` | Нагрузка: тяжёлые запросы, индексы, N+1, подписки без фильтра, фоновые задачи с наложением запусков, кеширование, память/CPU | `## ⚡ Производительность` |
| Доменные ревьюеры проекта | См. ниже | Свои секции |
| `vibe-flow:orchestration-router` | **Отдельным сообщением после пачки** — чем реализовывать план | `## 🚀 Оркестрация реализации` |

- 🔴 **Правило расширения:** если в `.claude/agents/` проекта есть свои доменные ревьюеры плана (в их `description` написано, что они ревьюят план в Plan Mode / до `ExitPlanMode`) — запусти их **в той же пачке**, с тем же блоком про рубрику. Самоисключиться, если план их не касается, — их собственное дело
- `security-reviewer` и `performance-reviewer` **не дублируют** друг друга: security — безопасность и права, performance — нагрузка
- 🔴 **Файл плана ревьюеры меняют ТОЛЬКО через `Edit`** — дописать или заменить свою секцию. `Write` для файла плана запрещён: агенты пачки пишут в один файл одновременно, и перезапись целиком затирает секции соседей, дописанные после чтения. Доменному ревьюеру проекта, у которого в `tools` есть `Write`, допиши это правило в промпт
- Ревьюер, которому в плане нечего проверять, **самоисключается** («✅ не требуется») — это нормальный исход, а не сбой
- **Результаты всех ревьюеров** сообщать пользователю **ДО** `ExitPlanMode`, чтобы замечания вошли в план до одобрения
- **НЕ вызывать `ExitPlanMode`**, пока не отработал каждый ревьюер пачки

### 🧭 plan-reviewer

- **Цель:** перефразировать технический план простым языком, чтобы пользователь мог внести изменения ДО одобрения
- **НЕ вызывать `ExitPlanMode`**, пока пользователь не прочитал упрощённый план от `plan-reviewer`
- **Дописать в промпт `plan-reviewer`:**
  ```
  Проверь секцию «## 🔬 Проверить живьём»: все ли допущения плана о внешних
  системах в неё попали и каждое ли закрыто фактом, а не намерением. Допущение,
  оставшееся в тексте плана и не попавшее в таблицу, — это вычет по рубрике
  (−2.0, если от него зависит контроль доступа или источник данных, иначе −1.0).
  ```

### 🔒 access-control-reviewer

- **Цель:** новая фича не должна молча стать видна всем — и не должна молча оказаться не видна никому. Решение «кому включаем» принимается **явно**
- 🔴 **СПРОСИТЬ ПОЛЬЗОВАТЕЛЯ:** если субагент вернул строку `🔴 ТРЕБУЕТСЯ ВОПРОС ПОЛЬЗОВАТЕЛЮ`, главная сессия **ОБЯЗАНА** задать вопрос через `AskUserQuestion`, взяв `header`, `question` и все варианты ответа (`options`) **дословно** из блока `### ❓ Вопрос пользователю` в файле плана, и вписать ответ в план — **ДО** `ExitPlanMode`, чтобы решение вошло в реализацию
- **Почему спрашивает главная сессия, а не агент:** `AskUserQuestion` в субагентах недоступен — субагент только готовит вопрос
- **НЕ решать за пользователя:** «включим всем» / «только себе» / «потом разберёмся» без явного ответа — запрещено
- 🔴 **Порядок раскатки:** если доступ к фиче включается данными (флаг или настройка в БД), миграция данных применяется **первой**, деплой кода — **после**. Обратный порядок открывает окно, в котором фича видна не тем или погашена у всех
- **НЕ вызывать `ExitPlanMode`**, пока `access-control-reviewer` не отработал **и** (если он поднял маркер) пока ответ пользователя не записан в план

### 🧪 test-impact-reviewer

- **Цель:** на этапе плана (до кода) определить влияние на тесты — какие **обновить** (план меняет поведение покрытой функции), какие **новые** добавить (новая чистая логика / регресс на баг), либо что тесты **не требуются**. Если в проекте тестов нет вообще — честно сказать и предложить минимальный старт
- Субагент **сами тесты НЕ пишет и НЕ меняет** — только рекомендует
- 🔴 **СПРОСИТЬ ПОЛЬЗОВАТЕЛЯ:** если вердикт не «✅ не требуется», **ОБЯЗАТЕЛЬНО** через `AskUserQuestion` спросить, что делать (обновить существующие / добавить новые / и то и другое / пропустить) — **ДО** `ExitPlanMode`, и вписать ответ в план
- **НЕ вызывать `ExitPlanMode`**, пока `test-impact-reviewer` не отработал и пользователь не решил, что делать с тестами

### 🚀 orchestration-router

- 🔴 Запускать **ОТДЕЛЬНЫМ сообщением, после того как вся пачка ревьюеров вернулась** — не в той же пачке. Причины две: он должен видеть уже дописанные секции других ревьюеров (их правки меняют масштаб работы), и его запись в файл плана не должна совпасть по времени с их записью
- **Цель:** осознанно выбрать механизм реализации — **Workflow** (детерминированный JS-скрипт), **бригада агентов** (параллельные группы вызовов `Agent`) или **прямое выполнение**
- Сам ничего не запускает и не пишет скриптов — только рекомендует
- **ГОТЧА:** Workflow **требует явного «да» пользователя** — роутер только советует

## PLAN SCORING RULE

**Каждый ревьюер плана обязан выставить балл 0–10 по единой рубрике** — `${CLAUDE_SKILL_DIR}/rubric.md`.

- Ревьюеры пакета знают рубрику сами, но **блок ниже главная сессия дописывает в промпт КАЖДОМУ ревьюеру** — в том числе доменным ревьюерам проекта, которые о рубрике ничего не знают:
  ```
  Прочитай рубрику ${CLAUDE_SKILL_DIR}/rubric.md и заверши свою
  секцию строкой «**Оценка: X.X / 10** · блокирующих (critical/high): N» плюс
  строкой «Вычеты:» с перечислением каждого вычета и его веса. Балл выводится
  из вычетов, а не назначается.

  Гейт идёт НЕ по баллу, а по блокирующим: план держат только замечания
  critical (вес −4.0/−3.0) и high (вес −2.5/−2.0). Каждое такое замечание
  обязано называть сценарий отказа — при каких входах или состоянии что
  сломается. Замечание без сценария понижается до medium и гейт не держит.
  Не завышай severity «на всякий случай» и не занижай, чтобы прошло.
  ```
- **Балл Claude = МИНИМУМ по всем отработавшим ревьюерам.** Среднее запрещено: одна дыра в изоляции данных не должна компенсироваться высокими баллами за оркестрацию и тесты
- **Самоисключившиеся ревьюеры** («✅ не требуется») в расчёт минимума **не входят** — у них нет предмета оценки
- 🔴 **Балл без списка вычетов недействителен.** Ревьюер, вернувший «9.5» без расшифровки или без строки «блокирующих: N», считается не отработавшим — перезапросить у него вычеты

## CODEX CRITIC RULE

**Зачем:** ревьюеры Claude — это одна модель, проверяющая сама себя. Внешний критик на другой модели (Codex CLI; модель — из `~/.codex/config.toml` пользователя, reasoning effort `high`) ловит то, к чему у Claude слепое пятно: собственные архитектурные привычки и то, что уже «выглядит правильно».

**Критик опционален по установке, но обязателен, если установлен.** Наличие проверяет сам `vibe-flow:codex-plan-critic` первым шагом и возвращает один из трёх исходов:

| Исход агента | Что значит | Что делает главная сессия |
|---|---|---|
| `⚪️ Критик не установлен` | `codex` нет в `PATH` | Гейт держат ревьюеры Claude. **Один раз за сессию** сказать пользователю: «Внешний критик не установлен — гейт идёт по ревьюерам Claude. Поставить: `npm i -g @openai/codex` (или `brew install codex`), затем `codex login`». В следующих раундах не повторять |
| `❌ Критик недоступен` | Codex установлен, но не авторизован, упал, не вернул JSON или упёрся в таймаут | 🔴 **Гейт НЕ пройден.** Показать пользователю точную ошибку и спросить: чинить и ждать или идти без внешнего ревью под его ответственность. Ответ вписать в план. Молча продолжать запрещено |
| Отчёт `## 🧑‍⚖️ Внешнее ревью Codex` | Критик отработал | Разобрать каждое замечание (ниже) |

- 🔴 **Критик недоступен ≠ критик доволен.** Установленный, но упавший Codex — это не «прошёл» и не «не установлен». Это стоп с вопросом пользователю
- **Порядок:** запускать **после** всей пачки ревьюеров Claude, когда их секции и баллы уже в файле плана — критику передаётся план **вместе** с ними. Иначе он снимет баллы за то, что уже разобрано
- 🔴 **Codex НИЧЕГО не пишет** — ни в план, ни в репозиторий. Песочница `-s read-only`, у агента-обёртки нет `Edit`/`Write`. Владелец плана — главная сессия Claude
- 🔴 **Решение по каждому замечанию принимает Claude, не Codex и не пользователь поштучно.** Claude разбирает каждое замечание, принимает или отклоняет **с обоснованием** и показывает пользователю итоговую таблицу «принято / отклонено + почему» перед `ExitPlanMode`
- **Отклонять можно** — критик не начальник. Но отклонение без обоснования запрещено: в таблице должно быть написано, почему замечание неверно или неприменимо
- **Данные уходят наружу:** при первом запуске критика в сессии сказать пользователю одной строкой, что план и фрагменты кода отправляются внешнему провайдеру (OpenAI) — агент возвращает эту строку в отчёте раунда 1. Секреты (`.env*`, ключи, файлы доступов) Codex по шапке промпта не открывает
- **Правила проекта Codex берёт сам:** он запускается из корня проекта и читает `AGENTS.md`; если правила лежат только в `CLAUDE.md`, агент-обёртка велит ему прочитать и его
- ⚠️ **Готча Plan Mode:** харнесс может не дать агенту-обёртке писать даже во временную папку — и критик не запустится до `ExitPlanMode`. Тогда — с явным согласием пользователя — запускать его **сразу после `ExitPlanMode` и ДО первой правки кода**: гейт держит начало реализации, а не выход из плана
- **НЕ вызывать `ExitPlanMode`**, пока `codex-plan-critic` не отработал (или не вернул «не установлен») и его замечания не разобраны

## PLAN GATE RULE

**Гейт — по классу дефекта, а не по баллу.**

План уходит в реализацию, когда **не осталось открытых замечаний `critical` и `high`** — ни у ревьюеров Claude, ни у внешнего критика (если он установлен). Балл считается и показывается всегда, но сам по себе план не блокирует.

- **Открытое замечание** — то, которое не принято и не отклонено с обоснованием. Принятое и внесённое в план закрыто; отклонённое **с фактом** (`файл:строка` или ссылка на явное решение пользователя) закрыто тоже
- **Соответствие «вес ↔ severity»** — жёсткое, в `${CLAUDE_SKILL_DIR}/rubric.md`: −4.0/−3.0 = `critical`, −2.5/−2.0 = `high`, −1.5/−1.0 = `medium`, −0.5/−0.3 = `low`
- 🔴 **`critical`/`high` без сценария отказа не блокирует.** Замечание блокирующего класса обязано называть, при каких входах или состоянии что сломается. Без сценария оно понижается до `medium` — это защита от инфляции severity, которой числовой гейт не имел
- 🔴 **Отклонение — законный способ закрыть замечание, а не поражение.** При числовом гейте спорить было невыгодно: за четыре раунда одного плана из восемнадцати замечаний критика не было отклонено **ни одного** — критик де-факто получил право вето. Теперь отклонение с фактом закрывает пункт наравне с правкой

**Почему не «≥ 9.0 по обеим сторонам».** При весе −2.0 за рядовой дефект логики порог 9.0 означал «не более одного замечания веса 1.0» и для плана нетривиального размера был непроходим в принципе. На реальном плане критик дал 0.0 → 2.0 → 1.5, хотя план от раунда к раунду становился лучше и все замечания закрывались. В реализацию он ушёл решением пользователя мимо гейта — механизм, задуманный решающим, оказался декоративным. Порог не «снижен»: он заменён на тот, который измеряет опасность, а не количество.

**Если гейт не пройден — автоправка, до 3 раундов:**

1. Claude правит план по **принятым** замечаниям
2. Перезапускает тех ревьюеров, чьей зоны коснулась правка, — за новым баллом **и новым числом блокирующих**
3. Перезапускает `vibe-flow:codex-plan-critic` (если он установлен) с номером раунда и списком отклонённого **с обоснованием**
4. Гейт считается заново

🔴 **Лимит — 3 раунда, жёстко.** После третьего неудачного — **стоп**: показать пользователю оценки, историю раундов, что принято и что отклонено, и в чём именно расхождение. Дальше решает пользователь: править вручную, продавить план как есть или отказаться. Четвёртый раунд запускать запрещено — это сжигание токенов на несходящемся споре.

🔴 **Не смягчать severity, чтобы прошло.** Если у плана упорно остаются `critical`/`high` — это сигнал о плане, а не о слишком строгом гейте. Переназначать класс дефекта вопреки таблице весов запрещено; правило меняет только пользователь явным указанием. Понижение допустимо ровно по одному основанию — отсутствие сценария отказа у самого замечания.

**Показывать пользователю перед `ExitPlanMode`:**

```
## 🚦 Гейт плана

| Сторона | Балл (метрика) | Открытых critical/high |
|---|---|---|
| Claude (мин. по ревьюерам) | 8.5 | 0 ✅ |
| Codex (внешний критик) | 6.5 | 0 ✅ |

Гейт: ✅ пройден — блокирующих замечаний не осталось
Раундов пройдено: 2 из 3

**Замечания критика:**
| ID | Severity | Суть | Решение | Почему |
|---|---|---|---|---|
| C1 | critical | ... | ✅ принято | внесено в шаг 3 |
| C2 | high | ... | ❌ отклонено | проверка уже стоит, `src/api/orders.ts:42` |
| C3 | medium | ... | ✅ принято | внесено в «Риски» |
```

Если Codex не установлен — строка критика `⚪️ не установлен`, гейт по ревьюерам Claude. Если недоступен и пользователь решил идти без него — строка `❌ недоступен — решение пользователя`, и это решение записано в плане.

Балл в таблице остаётся: он показывает, насколько план хорош, и низкое число при пройденном гейте — законный повод сказать пользователю «прошло, но вот по каким пунктам план слабый».

## TEAM CREATE RULE

**После `ExitPlanMode` действовать по вердикту `orchestration-router`** (секция `## 🚀 Оркестрация реализации` в плане):

- **🔀 Бригада агентов** → автоматически, без вопросов:
  1. запустить `vibe-flow:team-planner` с путём к файлу плана → он определит параллельные группы, типы агентов, модели и effort и допишет `## 👥 Команда агентов` с готовыми промптами
  2. 🔴 **Основной путь — параллельные вызовы `Agent`:** каждая группа из секции — **одним сообщением** (по вызову `Agent` на агента): `subagent_type`, `model`, `effort` — из строки агента; промпт — из секции дословно (не придумывать заново) + строка `Рабочее дерево: <абсолютный путь>`
  3. Следующая группа — **только после результатов предыдущей**: проверить, что каждый агент сделал своё (файлы на месте, критерий «выполнено» выполнен); не сделал — уточнить промпт и перезапустить его
  4. Агенты бригады возвращают результат **финальным ответом**. Переписки через `SendMessage` нет — промпты самодостаточны
  5. Постшаги из секции — по порядку: `vibe-flow:test-runner` → [`vibe-flow:security-reviewer`, если секция его требует] → коммит через `scripts/git-safe-commit.sh` → `vibe-flow:release-gate` → `vibe-flow:dev-server-restart` (каждому — `Рабочее дерево: <путь>`)
  - **`TeamCreate` — только если доступен.** В Claude Code `TeamCreate`/`TaskCreate` экспериментальные и у многих их нет; параметр `team_name` у `Agent` без них **игнорируется**. Если инструмент есть — можно завести команду (`TeamCreate` → `TaskCreate` с теми же промптами → `Agent` с `team_name` → `TaskUpdate`); `SendMessage` уместен только для агентов, которые действительно в такой команде
  - **не использовать бригаду**, когда все шаги последовательные или задача тривиальная (1 файл) — тогда прямое выполнение
- **⚙️ Workflow** → 🔴 **только по явному «да» пользователя** в текущем сообщении: предложить Workflow и дождаться согласия; только после него — написать JS-скрипт и запустить `Workflow`. `team-planner` **не** запускать. **Инструмента `Workflow` нет** → сказать пользователю и предложить бригаду (`team-planner` + параллельные `Agent`) или прямое выполнение
- **▶️ Прямое выполнение** → основная сессия реализует сама, без `team-planner`/бригады/`Workflow`

## PLAN FORMAT RULE

**Обязательный формат для всех планов в Plan Mode.**

**🔍 Этап 1 — выбор подхода (перед планом):**
Перед детальным планом — предложить пользователю **ТОП-3 варианта решения** через `AskUserQuestion`:
```
Вариант 1: [Название]
✅ Плюсы: ...
❌ Минусы: ...

Вариант 2: [Название]
✅ Плюсы: ...
❌ Минусы: ...

Вариант 3: [Название]
✅ Плюсы: ...
❌ Минусы: ...
```
- Пользователь выбирает → только после этого пишется детальный план
- Выбор записать в план строкой `**Выбран подход:** <вариант> — выбор пользователя из ТОП-3` в секции «💡 Зачем»: по ней `plan-reviewer` поймёт, что сравнение уже было, и не будет строить ТОП-3 заново
- **Исключение:** для тривиальных задач (1 файл, очевидное решение) этап выбора можно пропустить

**📋 Этап 2 — детальный план (шаблон):**

```markdown
# 🎯 [Краткое название задачи]

## 💡 Зачем
[1-2 предложения: какая проблема, зачем это нужно]
**Выбран подход:** [вариант — выбор пользователя из ТОП-3; строку убрать, если этап выбора пропущен]

## 🛠️ Что делаем
[Простым языком: что именно будет сделано]

## 🔬 Проверить живьём
[ОБЯЗАТЕЛЬНА, если план опирается на внешние системы. Таблица «Допущение —
Чем проверено — Факт — На что влияет», каждая строка закрыта фактом.
См. LIVE FACTS RULE. Плану без внешних систем секция не нужна.]

## 📌 Шаги
1. **Описание шага** — `путь/к/файлу`
   - Что именно меняем
2. **Описание шага** — `путь/к/файлу`
   - Что именно меняем

## 📂 Файлы
- ✏️ Изменяем: `файл1`, `файл2`
- ➕ Создаём: `новый-файл`
- 🗑️ Удаляем: —

## ⚠️ Риски
- Описание риска 1 → Как предотвратить
- Описание риска 2 → Как предотвратить

## ✅ Проверка
- [ ] Что проверяем — описание действия
- [ ] Что проверяем — описание действия
```
