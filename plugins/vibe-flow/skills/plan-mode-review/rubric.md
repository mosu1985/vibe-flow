# Рубрика оценки плана (0–10)

Единая шкала для **обеих сторон** — ревьюеров Claude и внешнего критика Codex
(если он установлен). Один и тот же документ читают все, иначе баллы
несопоставимы и гейт бессмысленен.

## 🔴 Балл — метрика, гейт — по классу дефекта

Прочитай это до того, как считать. **Балл сам по себе план не блокирует.**

План уходит в реализацию, когда **не осталось открытых замечаний класса
`critical` и `high`** (колонка «Блокирует» в таблице весов). Балл считается и
показывается всегда — он говорит, насколько план хорош, — но решение принимает
severity, а не число.

**Почему так.** Раньше гейт был числовым: «≥ 9.0 по обеим сторонам». При весе
−2.0 за рядовой дефект логики это означало «не более одного замечания веса
1.0». Для плана нетривиального размера такой порог непроходим в принципе:
критик, нашедший хоть что-то существенное, математически не мог поставить 9.0.
На реальном плане внешний критик за несколько раундов дал 0.0 → 2.0 → 1.5;
план всё это время становился лучше, а число почти не двигалось — и в
реализацию он ушёл решением пользователя мимо гейта. Механизм, задуманный
решающим, стал декоративным. Теперь гейт измеряет то, что важно: осталась ли
**невыправленная опасная вещь**.

🔴 **Занижать severity, чтобы прошло, — то же самое, что подгонять балл.**
Обе стороны знают правило, и соблазн ровно тот же. `critical`/`high` ставится
по классу дефекта из таблицы, а не по желаемому исходу.

🔴 **`critical`/`high` требует сценария отказа.** Замечание блокирующего класса
обязано называть, **при каких входах или состоянии что именно сломается**
(«пользователь с отключённым доступом читает кеш, прогретый другим
пользователем, и получает чужие данные»). Замечание без сценария — это
наблюдение, а не дефект: оно автоматически понижается до `medium` и гейт не
держит. Это защита от инфляции severity, которой числовой гейт не имел.

## Как считается балл

Старт — **10.0**. За каждый найденный дефект вычитается вес из таблицы ниже.
Итог округляется до одного знака, минимум 0.0.

🔴 **Балл без списка вычетов недействителен.** Оценка «9.0» без перечисления
того, что именно стоило 1.0 балла, — это самооценка, а не измерение. Ревьюер,
не приложивший вычеты, считается не отработавшим.

🔴 **Балл ни под что не подгоняется.** Он ничего не открывает и не закрывает —
гейт идёт по severity, — поэтому единственная его задача честно показать
качество плана. Сначала перечисли дефекты, потом посчитай.

## Веса вычетов

Колонка «Severity» — единая для обеих сторон: ревьюер Claude называет класс
дефекта весом, внешний критик — словом, и это одно и то же. Соответствие
жёсткое, переназначать его нельзя.

| Вес | Severity | Блокирует | Класс дефекта | Примеры |
|---|---|---|---|---|
| **−4.0** | `critical` | 🔴 да | Ломает прод или теряет данные | Необратимая миграция без бэкапа; деплой кода раньше миграции данных, от которой он зависит; удаление колонки или поля, которое читает живой код |
| **−3.0** | `critical` | 🔴 да | Дыра в изоляции или правах | Запрос без фильтра по владельцу/арендатору (`user_id`, `tenant_id`, `organization_id`…); новая таблица без RLS или эндпоинт без проверки прав; новый раздел виден всем пользователям, а не тем, кому положен |
| **−2.5** | `high` | 🔴 да | Нарушено критическое правило проекта (из `CLAUDE.md`) | Временное решение или мок в production-коде; запись во внешнюю боевую систему без явного «да»; деплой без разрешения пользователя |
| **−2.0** | `high` | 🔴 да | Дефект логики плана | Шаг зависит от результата более позднего шага; не учтён существующий общий модуль → дублирование; неверный порядок раскатки |
| **−2.0** | `high` | 🔴 да | **Непроверенное допущение о внешней системе, на котором держится контроль доступа или источник данных** | «Поле `status` в ответе API покажет, что заказ оплачен»; «этот эндпоинт вернёт только записи текущего пользователя» — если от ответа зависит, какие данные утекут или откуда они берутся |
| **−1.5** | `medium` | нет | Нагрузка без оценки | Запрос без индекса на большой таблице; подписка на изменения без серверного фильтра; фоновая задача по расписанию с риском наложения запусков; N+1 |
| **−1.0** | `medium` | нет | Пробел в покрытии | Меняется покрытая тестами логика, а тесты не упомянуты; нет шага проверки для рискованного изменения |
| **−1.0** | `medium` | нет | Прочее непроверенное допущение о внешней системе | Формат поля, единица измерения, часовой пояс, имя типа — там, где ошибка даёт неверные цифры, но не открывает данные |
| **−0.5** | `low` | нет | Неполнота описания | Не указан путь к файлу; размытая формулировка шага; забыт один из языков интерфейса в многоязычном проекте |
| **−0.3** | `low` | нет | Косметика | Не соблюдён шаблон плана; нет секции «Риски» при наличии рисков |

🔴 **Два класса про допущения появились не из теории.** В одном реальном плане
предикат «запись относится к нужной категории» читал не то поле внешнего API —
поле с похожим именем, но другим смыслом, по которому нужная запись была
неотличима от посторонней. Это прошло **девять проходов ревью**: шесть
ревьюеров Claude и три раунда внешнего критика. Проверка требовала одного
живого запроса к API, а ревьюеры читают текст. Дефект доехал до прода и был
пойман уже смоуком в браузере. Отсюда секция `## 🔬 Проверить живьём` в
обязательном шаблоне плана и эти две строки в рубрике.

## Что НЕ является поводом для вычета

- **Стилистические предпочтения** — «я бы назвал функцию иначе», «лучше другой паттерн»
  без конкретного вреда
- **Вопросы, уже решённые пользователем явно** — если в плане записан ответ на
  `AskUserQuestion`, повторно снижать за это нельзя
- **Задачи вне объёма плана** — «заодно стоило бы отрефакторить X»
- **Отсутствие того, чего проект не использует** — например требование e2e-тестов
  там, где их нет в принципе, или RLS в проекте без базы данных

Вычет за такое — сам по себе дефект ревью: он завышает порог и заставляет крутить
лишние раунды.

## Формат вывода балла

Каждый ревьюер завершает свою секцию строкой:

```
**Оценка: 8.5 / 10** · блокирующих (critical/high): 0
Вычеты: −1.0 меняется покрытая логика calculateTotal, тесты не упомянуты; −0.5 не указан путь к файлу в шаге 3
```

Если дефектов нет:

```
**Оценка: 10.0 / 10** · блокирующих (critical/high): 0
Вычеты: нет
```

Если есть блокирующие — их обязательно перечислить отдельно, со сценарием
отказа у каждого:

```
**Оценка: 6.0 / 10** · блокирующих (critical/high): 2
Вычеты: −3.0 нет фильтра по владельцу в шаге 4; −2.0 шаг 2 использует таблицу, которую создаёт шаг 5; −1.0 нет теста на новый предикат
🔴 Блокирует:
- critical (−3.0) — шаг 4 читает таблицу заказов без фильтра по `tenant_id`.
  Отказ: пользователь клиента A открывает список и видит заказы клиента B.
- high (−2.0) — шаг 2 пишет в таблицу `invoices_archive`, которая появляется
  только в шаге 5. Отказ: при реализации по порядку первая же запись падает
  с «relation does not exist».
```

🔴 Строка «блокирующих: N» обязательна даже при нуле — по ней главная сессия
считает гейт. Секция без неё считается не отработавшей, ровно как балл без
вычетов.
